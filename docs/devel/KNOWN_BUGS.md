# Known bugs with the existing code

## DuetControlServer

### Fractional codes
- [x] If a user sends a fractional code, e.g. `M25.1`, the engine will treat it as the integer part, e.g. `M25`. Fixed by the code class table (MOTION_SYNCHRONISED_ACTIONS.md §5.1): a fraction without a table row runs the macro named after it if one exists and resolves as unsupported otherwise.
- [ ] Nothing maintains `job.layer`, so `JobMonitor.UpdateLayers` never records `job.layers[]` statistics and DWC's layer chart stays empty. RepRapFirmware's PrintMonitor derives the current layer from the Z height and the layer height reported by the file info.

### Read-ahead moves run after a feedhold purge
- [x] A pause's feedhold purges the queued moves and cancels the job's read-ahead, but the read-ahead codes ran on anyway and their moves executed while the machine was "pausing". The cancellation was aimed at a token nothing observed: the job file loop assigned its token to each code's `CancellationToken` property, and `Code.ExecuteAsync()` then overwrote that property with the channel token, so `StopReadingForPause` cancelled a token no job code held. Fixed by passing the job token into `ExecuteAsync` instead; the same defect was what let a pause hang behind a blocking `M116` (the `SystemTests` scenario `PauseInterruptsTemperatureWait` covers that case, and `PauseAndResumeMidJob` the moves).

### A job ended before the moves it had queued were made
- [x] A movement code finishes when its move is queued, so `DoFilePrint` reached the end of a job file seconds before the machine reached the end of the job: `stop.g` ran, `state.status` fell to `idle`, and an `M25` from a console was refused with "Cannot pause print, because no file is being printed!" while the head was still moving. RepRapFirmware does not close the file until every move has completed, for both of those reasons (GCodes.cpp:706). `DoFilePrint` now waits for standstill when the file runs out of codes, unless the job is already pausing, cancelling or aborting, where the pause sequence does its own waiting.

### Waiting for a full object model update never returned
- [x] `ObjectModel.WaitForFullUpdateAsync` waited on an event nothing raised: `FullyUpdated`/`FullyUpdatedAsync` had no callers, because a finished full model update is what the SPI model updater used to signal and DuetControlServer now owns the object model outright. Everything that awaited it hung for ever, `M26` and `M27` among them. The infrastructure is gone - the condition variable, its lock and the four methods - and with it the two waits in `M26` and `M27`, whose `inputs[].motionSystem` is a local field nothing writes either, and the one before the plugins start. The simulated-time loop in `JobProcessor` now waits on `WaitForUpdateAsync`, which every write of the object model raises, and the `SyncObjectModel` command completes at once because a caller holding the read lock already sees every effect that has happened.

## DuetSbcInterface

### The permanent motion arena was never given back
- [x] `MotionSystem::Init` reserved the 4 MB permanent arena and nothing ever released it, so the DDA ring each motion system allocated stayed allocated after the instance was destroyed. One instance per process is all DuetControlServer creates, so a machine never noticed; the `SystemTests` bench, which hosts DCS in-process once per scenario, ran out after about thirty scenarios and `MemoryArena::Allocate` aborted the whole test process. `Reserve`/`Release` now count their users - the bench compares one machine against another with two motion systems alive at once - the region is unmapped when the last of them goes, and `MotionSystem`'s destructor is what lets go. `MoveSegment`'s free list is reset at the same time: it is one static per process while the arena is not, so without that the next motion system would be handed recycled segments pointing into memory that had been unmapped.

### A stop recorded a position the machine never stopped at
- [x] `MovePlanner.StopEarlyAsync` resynchronised the planner from `GetMotorPositions`, which reports what the drives have been commanded as of the last completed *segment*. A stop cannot recall a move whose segments are already on their way to the boards, so those moves carry the machine on after the stop is planned and that snapshot reads somewhere the machine is passing through rather than the place it stops - a pause one second into a 190 mm move recorded X2.5, the end of the acceleration ramp, while the head came to rest at X190. The pause restore point, the interpreter position and `pause.g`'s park move were all computed from it. The stop now reports the endpoints of the last move left in the ring after the purge, which is where the machine will come to rest and the same value RepRapFirmware takes from the same place (`DDARing::PauseMoves`, DDARing.cpp:647). `ResyncFromEngine` keeps its callers - homing, probing and a rejected submission - and now says that it is only right at standstill.

### A resume ran the rest of the job under the token the pause had cancelled
- [x] `StopReadingForPause` replaces the job's cancellation source, and only the paths that had a code in flight when the pause landed re-read it as they unwind. A pause that lands with nothing in flight - which is any pause after the file has been read to its end, now that a job outlives its reading - left `DoFilePrint` holding the cancelled token, so every code read after `M24` was cancelled as it was executed and the job ended having silently skipped the rest of the file. The loop now takes the live token where it resumes.

### A stop purged the ring but not the moves already submitted to it
- [x] `DrainFeedholds` empties the ring, and `DrainSubmissions` runs after it in the same pass of the motion loop and fed it every move DuetControlServer had already handed over - so the machine set off again after coming to rest and worked through a path it had been told to abandon, which is what left `M25` waiting tens of seconds for a standstill that a 60-second code timeout could outlast. Only reachable with segmentation on, because one G-code is one move otherwise and nothing is ever part-way through submitting when a stop lands. The stop now discards what it had been given for the ring it stopped; nothing is lost, because it reports the earliest move it purged and everything still waiting was submitted after that.

### A refused submission put the planner back to the wrong place
- [x] `MotionService::CanAddMove` asks the ring, which does not see the moves DuetControlServer has submitted but the motion thread has not taken up yet, so a code that submits hundreds of segments in one burst can overflow the submission queue and have a move refused after being told there was room. That is recoverable - the move is retried - but the recovery called `ResyncFromEngine`, putting the builder where the machine had *got to*, a whole queue of moves behind the end of what had been planned, so the retry was measured from somewhere the queue had long passed. The rollback now restores the endpoints the builder held before the build advanced them. The overflow itself remains: `CanAddMove` should account for what is already in the queue.

### A pause could wait for ever on codes the stop had orphaned
- [x] Found on hardware. A Deferred-class code is dispatched without being awaited and its handler waits for the move it was anchored to, and the pause cancelled the owed ones only `if (held.MovesPurged > 0)`. A stop that comes to rest without dropping anything from the ring names no purge boundary, so nothing cancelled them - and a stop discards what was on its way to the ring as well as what was in it, so their anchors will never retire. `PauseAsync` then waited on them in its standstill wait, which runs on the shutdown token alone, and `M25` never returned (`M122` reporting `processing, pausing` with `> Executing M25`). The stop now reports the last move it leaves standing and the pause cancels everything anchored past it whenever the machine stopped. Reasoned from the hardware log: the bench reaches the same state without hanging, so there is no scenario that goes from red to green over this.

### A resume read the file back in a mode it was never written for
- [x] Found on hardware as a job's end position drifting across repeated pauses, reproduced by `PauseTwiceAroundDeferredCodes`. The job file is read ahead of the machine, so a `G90`, `G91`, `M82` or `M83` further down the file may already have run by the time a stop lands - a job whose last line is `G90` does exactly that - and rewinding the file position does not undo it. The interrupted line was then re-read in the wrong mode, which turns a relative distance into an absolute target: a job of four `G1 X100` under `G91` tracked 94, 156, 221, then *backwards* to 156 and 100, ending at 100 instead of 400. The fractions were right throughout; the mode was not. RepRapFirmware cannot reach this because it reads one code at a time, gated by the movement queue, and so never runs past the point it may stop at. The restore point already carried the modal G command and the feed rate because a re-read line may name neither; the distance modes are recorded and put back with them, and are nullable because a stop that named no line has nothing to restore.

### A synchronous pause unwinds the macros under the token it has just cancelled
- [x] `PauseAsync` is called with the job token for `M226`, `M600`, `M601`, `M25` from the file and the deferred pause; `StopReadingForPause` cancels it, and `AbandonMacrosForPauseAsync` is awaited with it one statement before the sequence switches to the shutdown token. With a deferred code pending or a macro on the stack the sequence throws, settles to `Paused`, and skips the flush, the standstill wait, the restore point and `pause.g`. JOB_CONTROL_CONCURRENCY.md R4. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### The job reader parks before the pause has said where to rewind to
- [x] `PauseAsync` sets `Pausing` and raises `PurgeGeneration` before it has taken the resume point, and `StopReadingForPause`, which stores `_pausePosition` and sets `_pausePending`, runs in a later lock window. The submission in flight aborts on the generation change, `DoFilePrint` stops reading on `Pausing`, reaches the end of the file and parks with `_pausePosition` still null, rewinding to the end of the last completed code. The position and the pending flag land after the park, so the resume reads from the wrong line and, on reaching the end of the file again, parks a second time and rewinds to the position the pause had recorded: an absolute job of four lines travels 800 mm for a 400 mm file, a relative one over-travels by a line. `SteppedPauseTests` fails at 6 of 22 points for the absolute job and 3 for the relative one on this tree; the log shows `paused at byte 44 (no fpos from firmware), reason 0` logged before `Stopped the machine early`. [JOB_CONTROL_CONCURRENCY.md](JOB_CONTROL_CONCURRENCY.md) R1. Answered by the job actor: the reader is told where to rewind to and reports when it has, so it cannot park before the point exists. The stepped sweep is the acceptance test for it and has not yet been run on a bench whose results are a function of the scenario, which is [DETERMINISTIC_BENCH.md](DETERMINISTIC_BENCH.md).

### A stop that purges nothing from the ring still discards the submission queue, and the resume point does not know
- [x] `DDARing::Feedhold` may stop after the last provisional DDA, so `stopped == true` with `movesPurged == 0`, and `DrainFeedholds` then discards every move DuetControlServer had submitted but the ring had not taken. `TakeJobResumePoint` branches on `MovesPurged` and never reads `LastSurvivingMoveId`: with the interrupted code's record already released it returns null and the reader rewinds to the end of the file, so the discarded moves are never made; with the record still live, `SegmentsQueued` counts the discarded segments and the fraction over-reports. The 365 and 380 mm pause points of `SteppedPauseTests` are the first case. JOB_CONTROL_CONCURRENCY.md R2. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### The job monitor and the file reader take the object model and file locks in opposite orders
- [x] `JobMonitor.PublishAsync` holds the object model write lock and takes the job file's lock inside it; `CodeFile.ReadCodeAsync` holds the file lock and takes the object model read lock inside it, once per code, on `CancellationToken.None`. The two meet once the timing lands and neither can proceed, with the object model held for writing by the task that cannot. JOB_CONTROL_CONCURRENCY.md R9. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### A simulation before any job has finished never ends, and one after a finished job takes that job's duration
- [x] `ExecuteAsync` waits for `job.lastDuration` before it tears a simulation down, and `JobMonitor` writes that field only once it sees `IsProcessing` false, which the teardown is what clears. With `M37 F1`, the default, a simulation run before any job has finished waits for ever and no further job can be selected; one run after any finished job, simulated or not, reads that job's duration into the file. `M37SimulatesAFile` uses `F0` and does not reach the wait. JOB_CONTROL_CONCURRENCY.md R15. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### M0 with no job runs nothing after a job has ended

After any job has ended, `M0` from a console returns at the guard: no `stop.g`, no heaters off, against the comment on the guard that says it must work every time. JOB_CONTROL_CONCURRENCY.md R5. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### A read-ahead code dispatched between the stop and the token cancel restarts the machine or hangs the pause
- [x] `PauseAsync` cancels the job token one lock window after `StopEarlyAsync` returns. ### `M2` while paused leaves the reader parked and the job never torn down

### A pause is accepted while the end-of-job `stop.g` runs

### `M32` or `M23` from inside the job file deadlocks the job
- [x] `HandleSelectFileAsync` allows a file-channel `M32`, and `SelectFileAsync` then waits on `_finished`, which `ExecuteAsync` notifies only after `DoFilePrint` returns; `DoFilePrint` is awaiting the `M32` code's own task. The `File` channel is held until DCS restarts, and every later `M23`, `M32` and `M0` blocks behind it. The wait is on `ApplicationStopping`, so cancelling the job does not release it. An `M32` inside `stop.g` hangs the same way. JOB_CONTROL_CONCURRENCY.md R6. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### `M24` while a job is being cancelled starts it again
- [x] `ResumeAsync` refuses `Pausing` and `Resuming` but not `Cancelling`, and `PauseState == Paused` is false there, so `M24` during `cancel.g` takes the "start a selected file" path: `start.g` runs on the `File` channel while `cancel.g` runs on the caller's, `Resume()` overwrites `Cancelling` with `NotPaused` so the status reads idle mid-cancel, and the teardown runs under the still-executing `StopAsync`. JOB_CONTROL_CONCURRENCY.md R8. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### Replacing a running job reports it as finished
- [x] `SelectFileAsync` cancels the previous job through `Cancel()`, which records `IsCancelled = IsPaused`. For a running job that is false, so the teardown logs "Finished job file", runs `stop.g` rather than `cancel.g`, and writes `lastFileCancelled = false` for a job the operator replaced. The reason a job ended is derived three times from three inputs and they agree only because `M0` from a non-file channel is refused unless the job is paused. JOB_CONTROL_CONCURRENCY.md R11. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### An abort or cancel during `Pausing` leaves `pause.g` running against the stop
- [x] `Abort()` and `Cancel()` test only `IsFileSelected` before writing `NotPaused` and notifying `_resume`. Landing between `PauseAsync`'s first lock window and its `finally`, they leave `pause.g` running on the commanding channel under `ApplicationStopping` while the woken reader exits and `ExecuteAsync` runs `StopAsync(Abort)`: heaters and spindles are switched off under a macro that is parking the head, and `PauseAsync`'s `finally` finds `NotPaused` and settles nothing. JOB_CONTROL_CONCURRENCY.md R14. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### A pause that throws before its second lock window rewinds to the previous pause
- [x] Between setting `Pausing` and `StopReadingForPause`, `PauseAsync` awaits on the caller's channel token. If that token is cancelled (`M112`, `M999`, a dropped connection) the sequence throws after the engine has already executed the queued stop, the `finally` promotes to `Paused`, and `_pausePosition` still holds the previous pause's value because only `SelectFileAsync` clears it. The reader parks and rewinds there, and `M24` drives the head to the previous pause's restore point. JOB_CONTROL_CONCURRENCY.md R17. Answered by the job actor: the transition table, the reader being told where to rewind to and the rewind point coming from the move the engine says survives leave the interleaving no way to happen.

### A deferred code stalls the moves behind it
- [ ] Found on hardware as a stutter whenever a deferred command is sent, with `Underruns [0, 96]` on the ring to go with it. A deferred code's handler runs on its channel's `ProcessInternally` stage, and the channel submits no further moves while it runs, so the ring drains. The `Movement delay` in the same report is the scheduling horizon and is constant; it is not this.
